# M10-006 — Portability Remediation & Platform Hardening

Status: ACCEPTED

## Purpose

Take the explicit portability friction measured in M10-005 and harden the reusable platform so future community onboarding requires less manual remediation without hiding community-specific or source-specific behavior inside reusable core semantics.

## Accepted hardening

M10-006 consumes the exact four remediation items measured in the Rancho Vistoso M10-005 pilot:

- `COM-001` — Rancho Vistoso community taxonomy;
- `SRC-001` — MLSSAZ listing compatibility;
- `SRC-002` — Pima County Assessor parcel compatibility;
- `SRC-003` — Pima County Recorder document-index compatibility.

The hardening does **not** reclassify these differences.

Retained classifications:

- `COM-001` remains `COMMUNITY_SPECIFIC`;
- `SRC-001` remains `SOURCE_SPECIFIC`;
- `SRC-002` remains `SOURCE_SPECIFIC`;
- `SRC-003` remains `SOURCE_SPECIFIC`.

What changed is how the platform consumes them. Each item is now a governed profile input with schema/validation rules instead of a one-off manual remediation step.

## Measured before/after result

M10-005 measured:

- manual remediation: **4/11 work items**.

M10-006 hardened replay measured:

- manual remediation: **0/11 work items**;
- reduction: **4 work items**;
- retained community/source classifications: **4/4 unchanged**.

The reduction comes from reusable validation/profile interfaces. It does not come from pretending MLSSAZ, Pima County, Oro Valley, or Rancho Vistoso semantics are universal.

## Guardrails

- community/source classifications may not silently change during hardening;
- every hardening disposition must exactly cover an M10-005 remediation item;
- every hardened profile must exist and validate;
- listing-source profiles cannot imply proprietary MLS record access or credentials;
- accepted parent baseline mutation fails closed;
- the original M10-005 evidence remains immutable;
- hidden community/source defaults remain prohibited.
